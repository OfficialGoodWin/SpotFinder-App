# Photo preparation and upload

Spot, draft, edit, and community POI photo selection use the same preparation dialog. It preserves the full frame and aspect ratio unless the person chooses Crop. Resize never upscales. The dialog previews the encoded result, its dimensions, and its approximate size before accepting it.

The client accepts JPEG, PNG, WebP, and HEIC/HEIF only when the file signature matches. HEIC/HEIF is converted to JPEG only if the browser can decode it; unsupported devices receive a conversion instruction. Inputs are limited to 40 MB, 32,768 pixels on either side, and 100 million pixels to bound decoding work. The prepared JPEG is at most 4,096 pixels on either side, 16 million pixels, and 5 MB. Storage rules retain their existing 5 MB JPEG requirement. The 40 MB source cap is a client memory policy, not a Storage upload allowance.

The browser uses a file-backed object URL and requests downscaled bitmap decoding when supported. It never sends the original HEIC, PNG, or WebP to Storage. Canvas JPEG encoding removes ordinary EXIF metadata, including precise GPS tags. The server rejects new JPEG uploads with EXIF, IPTC, or comment segments. EXIF orientation is applied during bitmap decoding. Browsers without downscaled decoding may need to decode a large source in memory; failures instruct the person to export a smaller JPEG. No external image conversion service is used.

Processed photos remain `File` objects in the existing draft flows. Signed-in drafts store private JPEG blobs in Firebase Storage and guest drafts store them in IndexedDB. A restored draft file is re-encoded before a later public upload so a stored filename alone cannot bypass metadata removal. A public URL is returned only after Storage completes and the authenticated `validateCommunityPhoto` callable checks the object's owner path, metadata, JPEG structure, size, and dimensions. Draft publication also checks JPEG bytes before promotion. Official POI editing currently supports approved photo metadata only; it has no photo upload control.

Deploy the new Cloud Function before deploying the web build, then deploy both through the normal reviewed workflow. Do not deploy this client alone: it requires `validateCommunityPhoto`. Storage rules were not changed. Storage rules cannot examine file bytes, and callers that bypass the application can still upload an object with a forged JPEG content type. Enforcing validation before every public read would require a future private staging and server promotion path.
