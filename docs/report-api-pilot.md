## Current flow and bypasses

`src/components/moderation/ReportDialog.jsx` handles spot, POI, photo, and social post reports for signed-in, email-verified users. `src/api/firebaseClient.js:1314` obtains a reCAPTCHA Enterprise token and calls `functions/index.js:1438` (`submitReport`). The callable checks verified Auth, submission blocks, reason, reCAPTCHA, UID/IP/device blocks, 8/UID/hour and 20/IP/hour transactional counters, then queries for an open report and writes `reports`. Admin moderation uses `adminResolveReport`, `adminDeleteReport`, and `adminBlockReporter` callables. `ReportAnythingButton.jsx` also calls `submitGeneralReport`, but its `other` target and categories do not match the callable's allowed reasons; it is outside this content-report pilot.

`firestore.rules` already has `allow create: if false` for `reports` and denies client access to `report_blocks`. No rule change is required to stop direct report creation. Keep this rule during rollout and rollback. The **old callable is a remaining alternate path** around the new pilot's App Check requirement, challenge threshold, idempotency, and target checks. A verified user can still invoke it directly with a valid reCAPTCHA Enterprise token; its separate UID/IP limits remain, but they are weaker than a single shared policy. Do not describe report protection as complete while it exists. Admin SDK writes bypass rules, so the Vercel route validates its own authorization and fields.

## API contract and policy

The browser sends a Firebase ID token in `Authorization: Bearer`, a UUID-like `idempotencyKey`, the existing report fields, and a Turnstile token only after `CHALLENGE_REQUIRED`. Server derives UID and email from a verified, non-anonymous, email-verified Firebase ID token; a body UID is rejected. JSON is capped at 8 KiB, with strict field names and lengths. Spot, photo, and social targets are looked up server-side; POIs lack a Firestore source of truth and receive syntax validation only. Firestore-backed target snapshots are derived server-side. POI snapshot text remains client-supplied and must be treated as untrusted by moderators.

| Outcome | Policy and response |
| --- | --- |
| Normal | First two accepted reports per UID/hour need no Turnstile. |
| Challenge | Third and later reports in the hour return `403 CHALLENGE_REQUIRED` unless a fresh `submit_report` Turnstile token passes Siteverify for an allowed hostname. A challenge only applies to this submission. |
| Short cooldown | Four accepted reports within five minutes lead to `429 REPORT_COOLDOWN` with `Retry-After`. |
| Hard cap | Eight accepted reports within one hour lead to `429 REPORT_HARD_LIMIT` with `Retry-After`, regardless of Turnstile. |
| Duplicate | One open report per UID and target. Bounded 24-hour target and idempotency claims live inside the existing per-UID `server_rate_limits` document; the same transaction prevents parallel duplicate API writes. Existing open reports are queried during transition. |
| Block | Existing UID/device report blocks and unexpired submission blocks are checked. No client-supplied IP header is trusted. This pilot leaves `ip_hash` null; Vercel WAF may provide an optional coarse network filter. |

No counter write occurs for malformed or unauthenticated requests, duplicate requests, rejected challenges, cooldowns, or hard caps. The accepted transaction reads one existing account limit document and writes two documents: the bounded counter/claim document and the report. Expired claim entries are pruned on acceptance and each map is capped at 193 entries, so storage cannot grow with every request. Preflight reads up to three block documents, one target document for Firestore-backed targets, and performs one bounded open-report query. Thus a typical accepted Firestore-backed report is **about 5 document reads plus the query result and 2 writes**, subject to Firestore transaction retries and query billing. A rejected malformed/unauthenticated request uses zero Firestore operations; a challenged or capped valid request still incurs the preflight reads and one transactional read but zero writes. This is deliberately limited to rare submissions, never public map reads. The legacy callable has separate counters and can raise total cost until retired.

## Setup, rollout, rollback

Required Vercel server environment names: `FIREBASE_PROJECT_ID`, `FIREBASE_CLIENT_EMAIL`, `FIREBASE_PRIVATE_KEY`, `FIREBASE_ALLOWED_APP_IDS`, `TURNSTILE_SECRET_KEY`, `TURNSTILE_ALLOWED_HOSTNAMES`, `REPORT_API_ENABLED`, and, for production, `REPORT_API_PRODUCTION_APPROVED`. Client build names: `VITE_REPORT_API_PILOT_ENABLED`, `VITE_TURNSTILE_SITE_KEY`, and the public `VITE_FIREBASE_APP_CHECK_SITE_KEY` registered to the exact Firebase web app. Never put the Turnstile secret or Admin credentials in a `VITE_` variable. Existing Admin credential convention is reused. Turnstile's official test site key and secret may be used **only in local/preview tests**, with mocked Siteverify for unit tests. Firebase App Check test/debug tokens must belong only to a separate development registration, never the production app.

Create a Turnstile widget for the exact production and preview hostnames, obtain separate public site key and server secret, and allow the `submit_report` action. `vercel.json` now includes the Turnstile script, frame, and connect origins for the eventual client challenge. Do not proxy DNS or configure WAF to make the widget work. A future WAF rule may filter obvious floods at the edge but cannot replace the per-UID transaction.

1. Run local unit tests and Firestore rules test with a `demo-` emulator project and synthetic credentials. Verify the old callable still works in the current deployment.
2. Deploy the disabled endpoint and CSP only after review. Confirm `REPORT_API_DISABLED` in preview and production. No live data is accessed by this disabled check.
3. Enable only a preview environment with test Turnstile credentials, synthetic users and emulator or isolated nonproduction Firebase project. Exercise challenge, retry, idempotency, and admin moderation.
4. Set the real server credentials, exact Firebase App ID allowlist, production hostname list, and `REPORT_API_ENABLED`; deploy client opt-in only after confirming App Check, Firebase Auth, Turnstile, and moderation work. Turn on production approval last. Monitor errors, accepted reports, old callable invocations, and Firestore operations. Keep the existing callable during a short observation period so cached clients keep working.
5. **Cutover gate:** after old-client traffic is acceptably low and a separately approved Functions deployment is possible, make the legacy `submitReport` callable reject new submissions or delegate to the same shared policy. Do not merely hide its frontend call; a user can call it directly. Because Functions deployment is unavailable on Spark, eliminating this bypass may require an operational decision later. Do not upgrade billing here or claim bypass closure before that change is deployed and verified.
6. To roll back the pilot, disable the **client** flag and the **server** flag. The old callable remains available and Firestore direct report creation stays denied. If the legacy callable has later been retired, restore a previously verified secure endpoint rather than reopening direct writes or restoring an unrestricted callable.

Next pilots: migrate spot ratings/reviews, saves/likes, then publication and photo upload according to cost and abuse exposure. Each needs its own server authorization and atomic policy; do not reuse report thresholds. Public Firestore reads require separate query/caching work and are unaffected by this API.
