## Security, listener and costs

The feed listener accepts only a server-confirmed Firestore snapshot (`fromCache === false`). Cached-only, missing, malformed and full feeds fail closed. Rules permit anonymous `get` only for `spot_snapshot_revocation_feed/current`, deny collection listing, and deny all public writes to feed, tombstones, journal, failures and checkpoint. Rules tests covered unauthenticated reads and unauthorized writes. Guest mode uses the same public feed read. Firebase SDK App Check initialization is attempted outside emulator mode, but this checkout has `enforceAppCheck: false` on callable Functions and permits App Check initialization failure while enforcement is off. **Hosted enforcement was not verified** and must not be claimed.

One active page maintains one listener to one document. Multiple React subscribers share it. Foreground and online transitions restart it; old listener callbacks are ignored. Firestore may reconnect internally, so no strict limit on transport reconnections or billable reads is proven. The app performs no timer-based feed polling. The feed retains tombstones permanently and fails closed at 500 IDs. The public feed contains IDs only, no email, owner ID, precise coordinates or moderation notes. Old public JSON URLs and downloaded copies remain accessible outside current-client revocation behavior.

[Firestore bills document additions and updates delivered to listeners as reads](https://firebase.google.com/docs/firestore/pricing). Under the Phase 4 model of two feed updates, no reconnects and one hour of continuous activity, 1,000 tabs imply about 3,000 listener document reads versus 240,000 feed reads and Function invocations under 15-second polling. One reconnect that issues a fresh read adds about one read per tab. New sessions add one initial read each. Rule-dependent reads may add charges if rules use `get()`/`exists()`; this feed rule does not. A document read charge is separate from network egress and a long-lived connection. Emulator browser traffic and these model counts are not a billing invoice. CDN manifest refresh for both maps is at most 120 checks per active hour per tab while foregrounded, independent of feed reads. CDN transfer and Firestore egress were not measured. A monetary estimate is withheld because the authorized staging project's location, plan and actual reconnect rate are unavailable; applying a regional unit price without them would be misleading.

## Publication completeness and visibility

Current `submitSpot`, owner edit/delete, admin edit/delete, photo changes and social indicator updates record relevant spot/journal changes with the spot update. A transition from published to non-public also adds a tombstone in the same transaction. Firestore triggers read current authoritative state for direct old-client writes, flag/report changes and other server mutations; duplicate or out-of-order event payloads do not replay older spot content. The publisher validates candidate regions and acknowledges only captured journal versions after deployment verification. A failed export leaves dirty entries. Bounded trigger retries write a privacy-safe failure marker when possible.

**Remaining failure window:** older deployed clients still have direct Firestore edit/delete permissions. Flag reconciliation and arbitrary bulk maintenance writes also depend on asynchronous triggers. A missed trigger can leave no dirty journal entry or urgent tombstone until manual full reconciliation; failure-marker writing can also fail during a Firestore outage. No exactly-once or no-loss guarantee exists. Keep old-client Rules compatible for now. A safe future cutover requires staged callable adoption, client-version observation, a scheduled bounded reconciliation and an explicit migration window before Rules forbid direct public spot mutations. Do not break current production clients in this phase.

The original Firestore viewport query includes `is_public == true` with status `published` **or** `pending_trust`. Snapshot export includes only approved `published` records and excludes review, flag and sensitive-location states. A synthetic test has 2 original-map visible spots and 1 snapshot-visible spot; **production counts were not accessed**. A newly submitted `pending_trust` spot can disappear from the original map when the snapshot flag is on, although My Spots and Nearby/Discover retain their existing data paths. Do not enable the original-map flag for users until product and moderation owners approve this visibility change. Do not weaken export filtering for parity.

## Packaging and protected Preview

The refreshed synthetic 250,000-spot export generated **384 region files + one manifest**, **92,446,044 raw snapshot bytes**, a **17,303-byte manifest** and **2,070,185-byte largest region**. Sum of per-region gzip/Brotli sizes was **4,196,161/3,516,188 bytes**. Local export took **10,512 ms**; reported peak RSS was **540,284 KiB**. The synthetic staging build with the original-map flag enabled had **489 files / 98,828,010 bytes**; non-snapshot output was **6,381,966 bytes** by subtraction. One synthetic edit changed one 2,051,394-byte region and local candidate creation took **9,861 ms**. This is not actual transfer size. Vercel source upload input, prebuilt upload size, deduplication, HTTP compression, edge cache hits, old deployment URL access and hosted response headers are **NOT TESTED**. The checkout has no `.vercel/project.json`, no Vercel CLI and no `VERCEL_TOKEN`. A local build cannot prove whether [Vercel's CLI static-file upload limit](https://vercel.com/docs/limits) applies to this exact deployment path. If this output were subject to a 100,000,000-byte limit, headroom would be only 1,171,990 bytes. No format-2 fields or coordinate precision were removed: doing so without a versioned client migration could make older readers reject or misplace markers. A versioned schema that omits repeated constants is the smallest candidate reduction to assess after Preview upload behavior is known.

## Rollout gates

- Emulator tests and protected Preview browser tests pass with staging data; production feature flags remain off.
- Rules, callable authorization, guest behavior and actual App Check policy are verified on the Preview target.
- All publication-relevant mutation paths have atomic journal writes or a proven reconciliation schedule and actionable failure alert.
- Revocation availability and client removal meet an agreed deadline across slow, backgrounded and reconnecting browsers; historical public URL limitations are accepted explicitly.
- Visibility treatment of `pending_trust` receives product/moderation approval.
- Vercel upload path, file limits, repeated-deployment reuse and delivery compression show safe headroom at 250,000 spots.
- Both maps preserve search, filters, marker selection, detail, clustering behavior, navigation, photos, private drafts, Nearby/Discover, auth and actions on mobile and desktop.
- Hosted cold/warm performance, Firestore read counts, network egress, browser memory and costs are measured; rollback retains live revocation checks and never restores hidden markers.
- Monitoring has an owner, alert destination, rehearsal and recovery instructions.

**Production NO-GO:** Preview, App Check enforcement, deployment size, visibility compatibility, trigger-independent publication recovery and sustained browser performance lack required evidence. Keep original-map flag disabled. No claim of 90% Firestore billing savings is supported by hosted invoices.
