# Public spot snapshots: Phase 3 staging handoff

**2026-10-31 status: local code and emulator/browser validation only. No Firebase Functions, Rules, Vercel Preview or production deployment occurred. Production NO-GO.** This extends [Phase 2](cdn-public-spot-map.md).

## State machine and safety boundary

Current `/spots` writes come from `submitSpot`, direct owner edits/deletes permitted by `firestore.rules`, admin moderation, flag/report triggers and other Functions. Phase 2's manually invoked publisher scanned `flags`, `reports`, then `spots`; a concurrent write during those pages could be missed. Its local directory rename prepared a candidate, not a Vercel deployment. The `/new` reader polled the immutable manifest but had no independent revocation source. An old region file could still contain a hidden spot.

Phase 3 adds `spot_snapshot_changes/{spotId}`. A Firestore `onWrite` trigger for spots and triggers for flags/reports call `recordSpotChange`. The transaction reads the **current** spot and prior per-spot journal, hashes only publication-relevant fields, and increments a monotonic version when the current state changes. Duplicate and out-of-order event delivery cannot replay an older event payload. Flag/report changes force a dirty journal entry. The admin `adminUpdateSpot` callable also awaits this update after a status change. Direct client edits/deletes still depend on triggers. The journal stores no spot details or account data.

The same transaction adds non-public IDs to a permanent server-owned revocation set and a single bounded feed document. The Preview API returns only IDs from that document, at most 499; at 500 or on a malformed/missing feed it returns 503. Firestore rules deny all client reads/writes to the journal, feed and checkpoint. The API is Preview-only, checks the isolated staging project, returns `no-store`, and has no write method. It does not use App Check; Preview protection is required, and a production public endpoint would need a separate abuse/App Check review. The `/new` snapshot reader requires a valid feed before loading the manifest, retries once, checks at most every 10 seconds per page and retains every revocation seen in that page. Opening a snapshot detail forces a fresh feed check before its live Firestore point read. The visible map refreshes every 15 seconds while active and on foreground return. On feed failure the snapshot map clears markers and shows its retry state; it does not query Firestore for the viewport. New sessions must complete the feed check before showing snapshot markers. Revoked IDs remain excluded from future static candidates, including full reconciliation.

**Revocations are permanent in this phase.** Restoring the same spot ID would require a reviewed generation/reset protocol; simply deleting a tombstone could let an old snapshot display it again. An already downloaded JSON file, old deployment URL or third-party copy remains obtainable. If historical public URLs must immediately stop serving sensitive content, static public JSON is the wrong delivery model: the minimum change is server-side access control or an operator-controlled removal/purge mechanism for every addressable copy, with a tested SLA. This overlay only controls cooperating current clients.

## Candidate and checkpoint

`publish.mjs --incremental` requires a previously validated local candidate. It reads up to 100 dirty journal documents, the single feed, current Firestore spot documents and bounded flag/report lookups for those IDs. It removes changed IDs from the prior public summaries, adds current approved projections, and regenerates content-addressed files. A moved spot disappears from its old region. All referenced files are read back and validated before the local manifest switch. A failed export leaves dirty journal entries unchanged. The candidate emits a sidecar receipt with captured journal versions. `confirm-preview.mjs` requires an explicitly approved staging target and HTTPS Vercel Preview origin; it verifies the hosted build target, manifest, **all** referenced region files and the revocation endpoint before transactionally acknowledging only journal versions that still match. Concurrent newer edits stay dirty. The checkpoint is stored in `spot_snapshot_publication/current`.

The manual full publisher remains for reconciliation. It scans authoritative flags/reports/spots under the existing read ceiling and excludes current revocations. The GitHub Actions workflow can optionally restore a reviewed previous candidate artifact by run ID; its seven-day retention is **not** durable storage. A missing baseline requires full reconciliation. The workflow still creates candidates only and does not deploy. No automatic deployment cadence or admin-action-to-static-publication deadline exists.

### Remaining journal gap

Firestore background triggers are asynchronous. A permanently failed trigger can leave a direct owner edit/delete unjournaled until manual full reconciliation. This code does **not** claim a no-loss guarantee or bounded failure alert. Before production, use a durable trigger retry/dead-letter or move all publication-relevant writes into trusted transactional endpoints, and configure an operational alert on failed trigger delivery, feed capacity and stale publication age. Do not enable snapshot Preview until the triggers and feed are installed in staging and checked. A Functions deployment that includes these exports must be reviewed carefully because the current production code file would include them.

## Staging preparation and manual Preview path

No Vercel project link, CLI, Preview credentials, staging ADC/WIF or protected deployment URL is available in this checkout. Configure Vercel Authentication with **Standard Protection** for Preview and verify the actual project setting before using staging test data. [Vercel documents Standard Protection](https://vercel.com/docs/deployment-protection) and [automation bypass headers](https://vercel.com/docs/deployment-protection/methods-to-bypass-deployment-protection/protection-bypass-automation). Keep any bypass token only in a protected local/CI secret and never print it.

After separate approval: deploy staging Rules and the three journal triggers plus the admin callable, initialize the feed **once** with a staging-only writer credential (`node scripts/public-spots/seed-staging.mjs STAGING_PROJECT --approved`), verify a synthetic hide updates the feed, then run the protected candidate workflow. Its reader identity needs only Firestore reads. A separate staging writer identity is needed for seeding and `confirm-preview.mjs`; do not grant writes to the candidate reader. Use staging web Firebase and App Check values, `FIREBASE_PROJECT_ID` equal to the staging project, `SPOTFINDER_SNAPSHOT_PREVIEW_APPROVED=true`, `VITE_PUBLIC_SPOT_SNAPSHOTS=true`, `VITE_SPOTFINDER_STAGE=staging` and `SPOTFINDER_SNAPSHOT_CANDIDATE_DIRECTORY` pointing to the extracted reviewed candidate. `build-vercel.mjs` uses `snapshot-staging` mode only when all explicit Preview guards pass; the normal production build remains a standard Vite build. Do not put private Admin credentials in `VITE_*` variables. The server endpoint uses the existing isolated Preview Admin SDK configuration.

With a locally linked Vercel project and an approved Preview credential, the intended commands are `vercel pull --yes --environment=preview`, `vercel build --target=preview`, inspect `.vercel/output/static/spot-snapshots`, then `vercel deploy --prebuilt` **without** `--prod`. These commands were **not run**. Vercel project settings must be checked for branch/environment scope and build output before use. After verifying the resulting protected URL, use a staging writer ADC and `SNAPSHOT_STAGING_CONFIRM=yes node scripts/public-spots/confirm-preview.mjs STAGING_PROJECT https://PREVIEW.vercel.app PATH_TO_CANDIDATE` to verify hosted bytes and checkpoint matching journal versions. Never run that command against production. Do not repeat deployments per spot; batch changes and keep the manual approval gate.

## Validation plan and measured local evidence

**Hosted CDN: NOT TESTED.** An approved protected Preview must measure uncached and warm requests in two browsers, `Cache-Control`, ETag, `x-vercel-cache`, delivered `Content-Encoding` and transfer bytes, manifest refresh across several deployments, immutable region reuse, missing regions, endpoint outage, old manifest/deployment URLs and active navigation during publication. Run repeated revocation trials with throttled network and background tabs. Record A: admin action to feed availability; B: feed availability to active removal; C: admin action to fresh-session suppression; D: admin action to deployed static manifest. The initial staging targets are B within 30 seconds while active and no marker after a successful mandatory feed check. Neither is a guarantee until hosted repeated trials pass.

Local demo browser observations: one feed update to active marker removal was **14,701 ms**; a fresh session showed zero revoked markers; endpoint loss produced the retry state and recovery did not resurrect the ID. The earlier local static hide to active removal in the same run was **14,667 ms**. Initial/warm marker display was **5,858/1,311 ms**. These are single local samples. A, C end-to-end, and D hosted were not measured. No production Firebase requests were observed in that browser run.

## Dataset and cost

An actual local disk export of **250,000 synthetic spots** produced **384 region files plus one manifest**, 92,446,044 raw bytes total, 17,303-byte manifest, and a 2,070,185-byte largest region. Region payloads compressed locally to 4,196,161 bytes gzip or 3,516,188 bytes Brotli quality 4. Export took 10,325 ms in the artifact-only run; post-measurement RSS was 453,197,824 bytes, and Node reported max RSS of 527,140 KiB. A second run built the full synthetic staging output with fake web config: **489 files, 98,822,020 bytes**, with 537,420 KiB reported max RSS. The representative synthetic cold/pan/zoom/return viewport journey made six mocked HTTP requests, transferring 2,698,737 raw JSON bytes or 95,043 gzip bytes in local compression. These are local compression results, not Vercel transfer measurements. The standard production `dist` build without candidate had 104 files and 6,365,794 bytes. Vercel's actual uploaded **source** packaging and plan enforcement are not measured. [Vercel's published limits](https://vercel.com/docs/limits) list a 100 MB Hobby CLI source upload cap and 15,000 source files; this candidate is near the byte threshold, and the build output size does not prove that upload will succeed. Treat 90 MB of measured upload input as a review threshold before attempting a protected Preview; the current local output already exceeds that conservative threshold. If approved field compaction cannot bring it down, a different delivery architecture needs separate cost and security approval. Do not compare compressed viewport transfer with the complete raw dataset. Keep six-decimal coordinates and the current public identifier/field allowlist. Further compacting fields or splitting dense regions requires separate map-behavior tests.

Cost model per run: full reconciliation reads at least all spot, flag and report documents plus one feed document; incremental candidate reads at most 101 journal results, one feed, up to 100 current spot documents and at most 102 flag/report documents per changed spot (limit 51 on each), then performs no Firestore writes. A trigger event reads current spot, journal and feed in one transaction and writes journal plus feed/tombstone when needed. Each active `/new` map currently makes up to four revocation HTTP requests per minute; each uncached request invokes a Vercel Function and reads one Firestore document, while manifest/region requests consume CDN transfer. At 1,000 continuously active tabs this would be up to 240,000 function invocations and feed reads per hour. This is an **estimate**, not observed traffic, and is a production cost blocker. CDN caching or a realtime single-document subscription may lower this cost but needs a reviewed freshness and App Check design. Deployment frequency is manually gated; no paid service is activated.

**Production decision: NO-GO.** Hosted behavior, trigger failure recovery, urgent-takedown guarantees, cost at load and old URL behavior are unresolved. The original map, Nearby and Discover remain on Firestore. Once these gates pass, the minimum migration is to reuse `readSnapshotSpots` in the original map behind its own build-time flag, preserve its existing full-detail point read, and test both map versions against the same revocation semantics before enabling it.
