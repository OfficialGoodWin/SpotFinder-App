## Dependency and failure map

`submitSpot` uses a trusted callable. It now writes the spot and initial dirty journal in the same Firestore transaction/batch. Current `updateSpot` and `deleteSpot` use owner callables; those and admin update/delete use `mutateSpotWithPublication`, which reads the current spot, journal and feed in a transaction. The existing photo-edit callable also writes a journal entry in its photo transaction when a snapshot field changes. A public-to-nonpublic mutation adds the tombstone in that transaction. Unauthorized owner mutations make no write. Publication-relevant edits increment a per-spot journal version. Ordinary description-only edits, photo reordering, likes, saves and map browsing do not add journal writes. **Rating aggregate changes also do not dirty the journal on every interaction**; snapshot rating values may lag until a manual full reconciliation or another change to that spot. Flag/report moderation, other server-owned mutations, and **older clients' direct owner writes** still rely on Firestore triggers. Triggers read current authoritative state, so duplicate or out-of-order event payloads cannot replay stale spot data; duplicate same-state events are no-ops. A trigger can nevertheless fail or arrive late. Failed processing is attempted twice locally and surfaced through `spot_snapshot_failures`; it is not an exactly-once guarantee.

The incremental publisher reads at most 100 dirty IDs per candidate, current spots, bounded moderation matches and the current feed. It builds against a validated previous candidate, removes moved/deleted IDs from old regions and validates the entire new manifest/file set. An export failure leaves journal entries dirty. The receipt records captured versions. `confirm-preview.mjs` checks the protected hosted build target, manifest, all region bytes and feed before `acknowledgePublishedCandidate` clears only matching versions. A newer edit stays dirty. The checkpoint rejects a candidate whose base revision differs from the last confirmed revision. Manual full reconciliation still scans authoritative `flags`, `reports` and `spots` under a read ceiling; it is needed to find missed trigger events.

**Remaining loss window:** old deployed clients may still use direct Firestore edit/delete because Rules preserve their existing access. A failed trigger for one of those writes may leave no journal or tombstone until a manual full reconciliation. Other server-owned mutations also rely on triggers. The two local attempts and failure marker are best effort: if Firestore is unavailable, the marker write can fail too. Firebase [documents at-least-once, unordered Firestore events](https://firebase.google.com/docs/functions/firestore-events) and [optional retry policies](https://firebase.google.com/docs/functions/retries). Platform retries were not enabled because they can repeat without a bounded attempt count. **No no-loss guarantee, deletion deadline or operational alert is claimed.** The CI health step is a failure signal, not configured paging. Full reconciliation can repair a missed static candidate but cannot retroactively guarantee that an old public URL ceased serving data.

## Revocation choice and safety

**Chosen: B, one Firestore document listener.** It reuses the existing Firebase client and App Check setup. The browser listens only to `spot_snapshot_revocation_feed/current`; Firestore Rules allow public `get` of that minimal document, deny list/write and keep journal/checkpoint/failure collections private. A server-confirmed snapshot (`metadata.fromCache === false`) is mandatory before `/new` displays snapshot markers. Offline or cached-only state clears markers. On recovery or foreground return, the listener restarts and requires a new server-confirmed snapshot. Observed tombstones remain in memory, so an older manifest or late region response cannot restore a revoked ID in that page. A detail click checks the same listener state before its live Firestore point read. The browser does not fall back to full Firestore viewport queries. Firestore [documents that initial listener data may come from local cache](https://firebase.google.com/docs/firestore/query-data/listen); treating that as fresh would be unsafe.

| Option | Evaluation |
| --- | --- |

| C — independent versioned manifest | A static Vercel asset cannot change independently of deployment. A dynamic epoch/feed would require an endpoint or direct Firestore document, returning to A or B. Incremental tombstone manifests would need retention and rollback rules for old clients and URLs. No new storage service was added. |

The feed retains tombstones permanently. At **500 IDs** the client and publisher fail closed; the Preview endpoint also returns 503. Tens of thousands of revocations are unsupported by the current single-document feed. Removing tombstones while old immutable URLs or supported cached clients exist can resurrect markers. No compaction is implemented. A versioned generation protocol needs a verified retirement policy for historical manifests, old clients and old URLs before any deletion of tombstones. Already downloaded public JSON and third-party copies cannot be erased by this listener. Existing public detail APIs still have their own live Firestore visibility rules; this phase adds the revocation check specifically to `/new` snapshot detail loading.

## Measured local behavior and cost model

The local browser used Chrome, Vite, the Firestore emulator and synthetic spot/feed documents. The final five successive feed writes had **write-start → marker removed** times of **109, 117, 55, 85 and 47 ms**. The respective emulator write-ack times were **82, 43, 44, 74 and 39 ms**; **write-ack → removal** was **27, 74, 11, 11 and 8 ms**. These are wall-clock samples, not hosted percentiles or an admin callable benchmark. A new tab suppressed the last revoked marker after its mandatory check in **797 ms** from navigation start. Initial/warm marker display in that run was **6,386/878 ms**. The separate static manifest hide took **30,097 ms**. Two tabs saw the first revocation, and feed deletion produced a retry state before recovery. No production Firebase requests were observed. Chrome reported JS heap use of **25.6 MB** near the first marker and **59.5 MB** after several reloads/trials; this is not a stable leak measurement because navigation and map state changed. The sampled CDP task-duration counter reached **0.836 seconds** in that run, also not a comparative CPU benchmark. Long-run memory growth, browser throttling, network edge delays and genuine admin-action timing were **not measured**. The provisional healthy foreground target of under 30 seconds is supported by five local listener updates, not guaranteed in production. Offline clients clear markers when the browser signals offline or the listener reports cached state; silent connection stalls and old public URLs remain limitations.

`node scripts/public-spots/cost-model.mjs` is reproducible and reports usage units, not money. Assumptions: each tab is continuously active for one hour, one synthetic 250,000-spot cold/pan/zoom/return journey per tab, two feed updates in that hour, zero reconnects, 100 tombstones (2,524-byte modeled feed). Daily visitors are **not** equivalent to these concurrent active tabs. [Firestore charges listener reads on document additions/updates and may charge again on reconnect](https://firebase.google.com/docs/firestore/pricing).

This model gives **80× fewer feed document reads** under its assumptions; reconnects and more frequent changes reduce that benefit. Snapshot bytes are local modeled raw JSON, not actual CDN transfer. Firestore read charges and network egress are separate. A 100-change candidate reads at most 101 journal results, one feed, 100 current spot documents and up to 10,200 bounded flag/report documents in the pathological case; candidate creation writes no Firestore documents. Confirmation writes at most 100 journal acknowledgements and one checkpoint. Each trusted spot create/edit/delete can write one journal document, with one feed plus tombstone document on a new revocation. Journal growth is one current document per spot; the feed adds one ID and tombstone document per revoked spot. Deployment frequency remains manually gated.

## Packaging and Preview boundary

The refreshed 250,000-spot synthetic disk export made **384 region files + one manifest**, **92,446,044 raw bytes**, with a **17,303-byte manifest** and **2,070,185-byte largest region**. Local gzip/Brotli totals for regions were **4,196,161 / 3,516,188 bytes**. The local staging build made **489 files / 98,826,840 bytes**. Max RSS reported by Node in the measured build was **545,748 KiB**. A single synthetic title edit changed **one region file of 2,051,394 bytes**; its local candidate rewrite took **9,658 ms** using the full in-memory synthetic input, so this is not a measured Firestore incremental read time. Actual source package bytes, prebuilt-upload bytes, Vercel file deduplication, delivered compression, CDN hit rate and hosted transfer are **NOT TESTED**. Vercel's [published limits](https://vercel.com/docs/limits) cannot establish whether this particular prebuilt packaging succeeds. Unchanged hashed regions are copied into the next local output; whether Vercel re-uploads them needs an approved Preview deployment and CLI measurement. The smallest near-term reduction is further allowlist/encoding review without changing coordinates or IDs; if the practical upload limit remains a blocker, a different delivery architecture requires separate approval.

The checkout still has no Vercel project linkage or CLI/Preview credential. Keep `SPOTFINDER_SNAPSHOT_PREVIEW_APPROVED=true`, `VITE_PUBLIC_SPOT_SNAPSHOTS=true`, `VITE_SPOTFINDER_STAGE=staging` and the candidate directory explicit only for a protected Preview build. Use staging-only Firebase identities, grant candidate/health readers only the needed read collections, and keep the checkpoint writer separate. Verify Vercel [Standard Protection](https://vercel.com/docs/deployment-protection) in the actual project before staging test data is used. The [automation bypass secret](https://vercel.com/docs/deployment-protection/methods-to-bypass-deployment-protection/protection-bypass-automation) belongs only in a protected test environment, never in frontend code. Phase 3's `vercel pull --yes --environment=preview`, `vercel build --target=preview`, inspect `.vercel/output`, and `vercel deploy --prebuilt` **without `--prod`** remain the manual route after separate approval. ## Verification and decision

Run locally with Java 21 and the demo emulator: `node --test tests/public-spot-snapshots.test.js tests/public-spot-revocation-state.test.js tests/owner-spot-publication-policy.test.js tests/snapshot-event-retry.test.js`; `firebase emulators:exec --only firestore --project demo-spotfinder-snapshots "node scripts/public-spots/emulator-phase3.mjs"`; the same wrapper for `node scripts/public-spots/emulator-validation.mjs` and `node scripts/public-spots/browser-staging.mjs`; `firebase emulators:exec --only firestore --project demo-spotfinder-snapshots "node --test tests/firestore-rules.test.js"`; `node scripts/public-spots/verify-staging-build.mjs`; and `node --max-old-space-size=4096 scripts/public-spots/measure-artifacts.mjs 250000 --build`. The focused Node tests passed **24/24** after the final retry helper change; emulator checks previously passed **23/23**, Firestore Rules suite **1/1**, local browser scenarios passed, and the staging/production build wrapper passed. A final emulator rerun after adding the health index was blocked because this shell currently exposes only Java 8 while Firebase Tools requires Java 21; the index query remains unverified in the emulator. An explicit `VERCEL_ENV=production` Vite build passed after the final code changes. The older full-reconciliation emulator check also passed in this phase's audit. Vercel Preview and hosted CDN tests were **NOT TESTED**.

**Production NO-GO.** Direct writes from old clients and server-owned trigger paths still lack guaranteed durable event recovery; no actual hosted listener/App Check/Preview behavior or cost was observed; the feed caps at 499 IDs; old public URLs remain retrievable; and the nearly 99 MB synthetic build lacks a real upload result. Next: deploy only to approved isolated staging, run repeated protected Preview latency/cache/upload trials, prove a reconciliation cadence and failure alert, and define a safe feed-generation protocol before considering a separate flag that lets the original map reuse the same snapshot reader.
